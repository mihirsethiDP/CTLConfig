# CloseTheLoop · Configuration proposal

A critique of the 28 September 2026 configuration handoff (`cfg-console-v4`) and a proposal for a simpler way to configure alerts, schedules and flows: SCADA draws the plant, a three-level library decides what each thing watches, the admin confirms. Static site, no build step.

- `index.html` — the proposal: what the handoff gets wrong, principles, simplifying by design, how it fits together, "SCADA builds it, the library decides" (with what the library reads from SCADA's equipment form), the surfaces including the What's enabled tab, who configures what (and why the prototype has no roles for now), the mapping to the approved PRD data model, open questions, how to use the prototype, and a dated change log (23 Oct 2026).
- `prototype.html` — the interactive console. Everything is in memory; **Reset data** restores the start state. Everything is editable as the Global Admin for now; there is no sign-in or persona switch. Two tabs: **Config** (everything you set) and **What's enabled** (read-only: what the plant team sees, derived from Config). **? Help** opens
 a panel that follows the screen and the step, and holds three demo switches: make the next save fail, start a new plant from SCADA, show the model underneath.
- `assets/data.js` — the sample plant (Manesar STP). `assets/catalogue.js` — the library (plant types, unit-process profiles with their skeleton sensors and alerts lists, 41 equipment types), the SCADA palette with every code and what it maps to, `SCADA_FORM` (SCADA's equipment form, question by question, per node type) and `FORM_RULES` (what the library reads from each answer), sample SCADA drawings (Bawal WTP, Manesar STP, Vedanta ETP) with sample form answers plus the change each receives later, `LAYOUT_FORMS` (a stand-in for the form answers the DigitalPaani export lacks), and `scadaFromLayout()`, which reads a real SCADA layout export. `assets/layout-digitalpaani.js` — the real layout of the **DigitalPaani** plant (an MBBR sewage plant with pressure filtration, UV, UF and water reuse; drawing version 157, site label Ireo Uptown): every cell of the export, without the drawing markup. The console reads it like any SCADA drawing. The export has no zones and no tags, so the console groups machines into zones by their names and makes each tag from its label (Reactor Feed Pump - 1 → RFP-1), and says so on the Connect step. `assets/flows.js` — 30 diagnostic flows, 83 action flows (maintenance, fixes, rounds, calibration, condition-based) and 74 root causes, bound to the library so every plant inherits them with the type. `assets/app.js` — core: the estate (four plants, one library, saved in localStorage), SCADA import, detection, inheritance, propagation, router, guide, export. `assets/runtime.js` — what happens after configuration: records, the notification pipeline, a clock, maintenance mode, sensor faults, planning arithmetic. `assets/operator.js` — the operator app and equipment card on a phone, with the pipeline beside it. `assets/estate.js` — the Estate and Maintenance pages. `assets/views.js` — setup steps (with the SCADA drawing, the step-3 cards and the every-machine rows on steps 4, 5, 7 and 8), equipment, flows, library, people, activity. `assets/enabled.js` — the What's enabled page. `assets/sheets.js` — stepper sheets. `assets/app.css`, `assets/app2.css`, `assets/theme-calm.css` — styles on DigitalPaani tokens; `assets/detect.css`, `assets/builder.css`, `assets/enabled.css` — the step-3 cards, the machine rows, and the What's enabled page.
