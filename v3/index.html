1 · Purpose and status

This is the build to start now. Close the Loop as a whole is not fully decided, so this doc draws a line: everything inside the configuration console is specified to the field, and everything that is still being decided is a named placeholder with an owner. Developers build the console in full. Placeholders are modelled so the console does not have to change shape when the decisions land.

The prototype at prototype.html is the reference for behaviour: five plants seeded at different depths, four personas, every add, edit and delete working, every pending decision listed on Go live (and shown as a dashed chip where one applies). Where this doc and the prototype disagree, the prototype wins on behaviour and this doc wins on contracts.

What the console is. One configuration per plant, in the hierarchy plant → unit process → control group → machine. It holds readings (from SCADA, entered by a person, or computed by a formula), limits, alerts, schedules and rounds, manual overrides, and the library check that compares the library's perfect picture with what the plant actually has. Plants read the published library; only a Global Admin edits it, on the console's Library page. People, roles and escalation live in User Center and are not in the console. It compiles the plant to the shape the rules engine consumes.
Helpers for every end user. Every screen has a "How this works ›" link and every drawer a "What do these fields mean? ›" link. Both open the help panel: the purpose of the screen, who may change what, how to do the common things, what every field means, the terms used, and the pitfalls. The content ships as assets/help.js and is part of the build, not an afterthought. Chips carry tooltips; severity tiers explain who is told; fields carry examples; every validation message is a sentence that says what to change.
What it is not. Not a second build for the library: a Global Admin authors the library inside this console (section 5.10), and plants read the published version. Not the rules engine, the notification service, the operator app, the analytical engine that evaluates formulas, or the event log. The console produces their inputs and names what it cannot yet produce.

2 · Two groups: console and library

Both are built in this console. The configuration is per plant and is edited by the plant's admins. The library is shared by every plant and is edited only by a Global Admin, as a draft that becomes a new version when published.

The rule between them. Plants read the published library through one interface (section 8); only the Global Admin's editor writes to it. An inherited item keeps its library ID (templateRef.lid, or libRef on a reading) and stays linked when the plant edits it: a change to a followed field (name, flow, cadence) is kept as a local change, and the library's later changes to that field are skipped. An item becomes source: "custom" only when the library no longer has it. When a new version is published, new items reach every plant at once as offers in its library check; changes to items a plant already follows wait until that plant is updated (5.10).

Where the library lives. The first version ships as a JSON document (the prototype's assets/library.js), loaded as version 2026.10.16. Every publish stores the whole library as a new version; plants record the version they follow. The read interface in section 8 is the same whether the store is a file or a service.

3 · Fundamental architecture

Principles the code must keep

  1. One configuration per plant. Every reading, alert and schedule sits on one subject in plant → unit process → control group → machine.
  2. The engine watches readings, nothing else. A SCADA tag, a value a person enters and a formula's result have the same shape, so an alert never cares where its value came from.
  3. Limits live on the reading. An alert uses them or overrides them for itself.
  4. The library offers, the console inherits, people override. A library item has a library ID that never changes. An inherited item gets its own plant ID and links to its library item by that library ID, so the library can rename anything and a plant can change its own copy. A plant's change to a name, flow or cadence is kept as a local change; Reset to library drops it. The library check lists every miss between the library's picture and the plant, and lets a miss be recorded as not installed.
  5. Severity is the console's whole say in who is told. People, roles and the ladder are User Center's. A stage, group or machine can be put under maintenance by hand, until a date; alerts below it stop firing.
  6. Nothing with records is deleted, everything is audited, the export is the whole plant. Delete archives; every change that can wake someone up is logged with before and after; the engine reads the export and never the console's tables.

4 · Entity model

Names as in the prototype's store. Identifiers are opaque strings. Every entity has id, plantId (except Plant), createdAt, and is scoped to one plant.

Two kinds of ID. The plant ID (id) belongs to the plant's own item and never leaves the plant. The library ID (lid, section 8) belongs to the library item it came from and is the same at every plant. An inherited item stores both: its own id, and the library ID in libRef (a reading that is a library sensor) or templateRef.lid (an alert, a schedule, a data input or formula reading). Every match between a plant and the library goes by library ID, never by name: the library check, the update plan, Not installed records, Reset to library. Names are free on both sides. A plant's edit to a followed field of a linked alert or schedule is recorded in overrides; the next library update skips that field and still applies the rest. Older saved data gets its links once, by name, when it loads. templateRef.type is the equipment type for a machine's items, the plant type or stage profile id for plant- and stage-level rounds, and absent for alerts and readings that come from a data input or formula.

5 · Screens and acceptance criteria

The shell is the DigitalPaani app's: navy top bar with the persona switch, breadcrumb, the legend strip, a lede sentence, stat tiles, a banner with the next action, a search box, uppercase group headers, white row cards with title, sub-line links and chips on the right. Phone width: cards stack, chips wrap, no horizontal scroll.

Keyboard. Every clickable row is a tab stop and opens on Enter or Space; a drawer takes the focus and gives it back to its row when it closes; Escape closes the top drawer, modal or help panel.

Where an item came from. Every plant item (stage, control group, machine, reading, alert, schedule) starts its row, and its drawer's sub-line, with a squared origin tag: Library (purple, a book) when it is inherited from the library and linked by library ID; SCADA (blue, a signal) when the SCADA drawing brought it; Added here (teal, a plus) when a person added it at this plant. A hand-added row also gets a faint teal wash; amber attention takes precedence when both apply. The tag is squared so it never reads as a status chip, has a fixed width so names line up, and its tooltip says what it means. The toolbar of each step shows the counts per origin, and each count is a filter: click one to show only those items (it gets a navy ring and an ×, the others dim), click it again or another to change, and a count of zero is disabled. It combines with Needs attention and the search; a stage header stays as the container of a matching machine; an empty result says which filters are on and offers Show everything; leaving the step clears it. Readings added from the library check are Library; data inputs and formulas offered by the library are Library; calibrations the library makes for every probe are Library. An item that began in the library but is no longer in it is shown as Added here, with "no longer follows the library" in its sub-line. Local changes on an inherited item show in purple in the sub-line ("local name").

5.1 Plants #/plants

  • Lists every plant the user may see, grouped by workspace, with machine, alert and schedule counts, the number of steps needing attention, the links Plant OS › and History ›, the steps that need attention as amber chips (each opens that step) or "All steps settled", how many steps are not started, and Live | Ready | Draft.
  • Add plant (Site Admin): name, type, capacity, workspace, code, and optionally "start from a drawing" SCADA import. From a drawing: zones become unit processes with a detected profile, machines and widgets become machines and readings, two machines of one type in one zone become a control group with duty and standby.
  • Edit plant: the same fields. The type is fixed once plant-wide rounds, data inputs or formulas came from it (remove them first to change it); when starting from a drawing, the drawing decides the type and the hooter settings are kept. Delete plant: confirm, cascade everything at the plant, audited.
  • Search by name. Tiles: plants, machines, alerts active, plants live.

5.2 Plant OS: one tab, five steps #/plant/:id

A plant has one tab, Plant OS, and inside it a flow of five steps shown as the pill bar: 1 Shape, 2 Sensors, 3 Alerts, 4 Work, 5 Go live. Each pill carries a status dot (green done, amber needs attention, grey not started) and a count. Opening a plant lands on the first step that needs attention. Each step ends with Back and Next. History sits behind a link in the header. There is no overview page: the pills are the overview.

Design rules applied, so the screens stay light. Hick's law: one tab, five steps, at most three buttons in a banner, one action per row. Miller's law: rows carry one line of text and at most three chips; counts live in the text, not in chips. Progressive disclosure: the library check and the pending decisions are collapsible panels that open only when they have something to say; edit, delete, status, reset and overrides live in the drawer, not on the row. Jakob's law: the shell, pills, legend, tiles, banner, search, group headers and row cards follow the app's Plants & modules page. Goal-gradient and Zeigarnik: the status dots and the Next button show how far a plant is and what is left. Tesler's law: the complexity that remains (limits, formulas, cadences) sits in drawers with field-level help, not on the lists.

  • Step status: Shape is done when machines exist and every one has a type; Sensors when nothing is missing against the library, every reading has limits and every reading passes validation; Alerts when at least one is active, none is a draft or invalid, and every machine with readings has an alert; Work when at least one schedule is active, no programme is missing, no schedule is a draft and every probe has a calibration; Go live when the plant is live (amber when ready).
  • Inherit everything offered applies every offered item in up to three passes (formulas wait for their inputs); it sits in the library check panel. Inherit… in the Alerts and Work banners opens a picker of that kind, grouped by level, with everything ticked; ticking nothing inherits nothing.
  • Attention first. Every step has a toggle All | Needs attention n, an amber banner that counts the reasons (3 × No limits yet · 2 × Draft, not firing), and rows that need attention carry an amber edge and one amber chip saying why, sorted to the top of their group. Rows that are fine carry only their status. One rule decides it for every list: attentionOf(kind, item) in the store.
  • Old routes keep working: overview and equipment open Shape, readings and coverage open Sensors, schedules opens Work, review opens Go live, audit opens History.

5.3 Step 1 · Shape #/plant/:id/shape

  • Grouped by unit process; within each, control groups first (navy chip), then machines. A machine's row: its origin tag, name, tag, and chips for duty or standby, its group and an override if any; one line with type (or "no library type"), tier and counts; on the right one amber chip with the first gap ("+n" when there are more). Clicking the row opens its drawer, which holds Edit, Delete and the override.
  • Add, edit, delete unit process (profile from the library). Deleting cascades its groups, machines, readings, alerts and schedules.
  • Add, edit, delete control group: name, unit process, members ticked from that unit process's machines. Ticking moves a machine between groups. Deleting a group removes its own readings and the alerts on them; the machines stay, ungrouped.
  • Add, edit, delete machine: tag (unique at the plant), name, unit process, control group, library type, tier with reason when it differs from the library, duty or standby of a sibling. Choosing a type for an untyped machine sets its tier to the library's.
  • In the Sensors step, each reading group header has ＋ SCADA tag, ＋ Data input and ＋ Formula, opening the reading drawer with that subject and that source preset; the unit process, control group and machine drawers end with the same links under Readings here, so a subject with no readings yet is reached there or through ＋ Reading. A link in a drawer with unsaved changes asks to save or cancel first. A SCADA reading needs its SCADA tag; the console makes tags only for entered and computed values (MAN-…, CALC-…). Sensors from the drawing arrive on the machine, on the unit process (zone sensors, pipe sensors with no machine at either end) or on the plant.
  • Manual override in the edit drawer of a unit process, a group or a machine: Running normally | Under maintenance, with an until-date and a reason, audited with who and since when. Rows show it; alerts under it show Maintenance and do not fire; schedules keep running (decision F14). The nearest override up the chain wins. Validation: reason and date required, date not in the past.
  • Search by name, tag or type.

5.4 Step 2 · Sensors #/plant/:id/sensors

  • The library check (5.7) sits at the top as a collapsible panel, open when something is missing. Then the readings, grouped by subject: the whole plant, then each unit process (its own readings, its control groups' readings, its machines' readings). Columns: reading and tag, kind, values from (SCADA | Entered: cadence and by whom, missed severity | Formula: expression and window), sample value, valid range, limits with Follows library | Custom. A state reading shows its kind as “state · its category”, its sample by the state's name (Running, Tripped), and in place of limits which state is a problem, or “information only”, plus “counts run-hours” for a run status. Clicking a row opens its drawer.
  • Add, edit, delete reading. The drawer: where it lives (any of the four levels), values come from (SCADA | a person enters it | a formula; a reading imported from SCADA cannot change input), name, tag (made by the console when blank: MAN-…, CALC-…, ending with the machine's tag or the stage), unit, kind (SCADA: Process, Probe, State, Counter; a data input: Lab or probe, Gauge, State or yes/no), for a state the signal category with its states listed (read-only when SCADA created the reading; no unit, range or bands), the input-specific section (7), valid range, the severity bands as the same coloured bar as on alerts with their direction, and the last value.
  • Every group header has ＋ SCADA tag, ＋ Data input and ＋ Formula, each opening the reading drawer on that subject with that source chosen. The unit process, control group and machine drawers end with Readings here: what lives on it, and the same three links. From the Library check, the same drawer opens prefilled from the library's definition (name, tag prefix, unit, kind, valid range, direction, and its preset bands, marked Follows library). The new reading links to the library sensor by its library ID.
  • Deleting a reading archives every alert on it that has records and removes the rest, each audited; a formula that used it loses that input and shows as invalid until rebound; a calibration of it goes back to draft; a run-hours schedule on a deleted run status or counter goes back to calendar only. Deleting a machine, stage or group does the same for everything on it, and frees a standby whose duty unit is gone.
  • Banner: the attention banner, listing readings without limits, readings that would not pass validation and expected sensors missing. The placeholder chips Manual entry screen and Analytical engine show in the reading drawer. A library sensor of kind computed (Recovery on UF and RO skids) arrives as a SCADA tag labelled "computed in SCADA": its expression uses pipe flows, which wait for connections.

5.5 Step 3 · Alerts #/plant/:id/alerts

  • Grouped by unit process (a control group's or machine's alert sits under its unit process) plus "About the whole plant". Row: name with severity tiers, one sentence (reading, direction, entry limit, how it closes, Lead's check, the flow it runs, clock overrides), chips: Maintenance if the subject is under maintenance, status; one action: Activate on a draft. The row starts with its origin tag; the sentence ends with any local change ("local name", "local flow") or "no longer follows the library". Everything else is in the drawer. A second alert on the same reading and direction shows an amber warning in the drawer; it does not block saving or activating.
  • Add, edit, delete alert. The drawer: one sentence of the alert with its severity in colour; 1 which reading (subject, then the reading: the subject's own first, then any at the plant); 2 severity bands, a coloured bar Normal → Caution → Minor → Major → Emergency showing the sensor's preset thresholds. By default the alert uses the sensor's bands (read-only here; change them on the reading and every alert follows) or switches to custom bands for this alert alone. A sensor without bands offers "Use the library preset" in one click; 3 hold and close on one line; 4 the flow, with its steps in view and Edit for this plant; More, collapsed: a Lead's check and the clocks; Status. For a state reading, section 2 is When it raises an issue: the category's states as tick boxes (its problem states ticked when the reading is picked) and the severity; section 3 is In that state for at least n minutes (0 raises it at once) and Closes when it leaves that state, or the operator says so. The sentence reads, for example, “when Trip contact is Tripped for 10 min; closes when it is no longer Tripped”.
  • Flow quick view: the flow name on an alert row or a schedule row opens its steps. Edit for this plant saves a copy of the flow for this plant only, audited, with Back to the library version; the alert's export carries the plant's steps under procedure.
  • Activate refuses with the first validation sentence. Saving as active with a gap keeps it as a draft and says why. Delete archives when the alert has or had records.
  • The drawer's sub-line shows the plant ID and, for an inherited alert, the library ID and any local changes. Changing the name or flow of an inherited alert keeps it linked: that field becomes a local change, library updates skip it, and every other field still follows. Clocks and a Lead's check are the plant's own choice.
  • Reset to library, on an inherited alert with local changes or custom bands, drops them and takes the library's current version in place: same plant ID, same records, the name rebuilt with its subject (for example "Line pressure high — BL-1"). The same button exists on schedules and on inherited readings.
  • An alert whose subject, or whose subject's group or stage, is under maintenance shows Maintenance with the reason and does not fire until it ends; the export carries suppressedBy.
  • Inherit… opens the picker filtered to alerts. Search by name or subject.

5.6 Step 4 · Work #/plant/:id/work

  • Grouped by the whole plant, then unit process. Row: name with the work type and Statutory, one sentence (cadence and run-hours, counted from, next due, performed by, Lead sign-off, the probe it calibrates, the steps it runs, hours), chips: the work type (Routine, Preventive maintenance, Calibration), Statutory, one amber attention chip, status; one action: Activate on a draft. The row starts with its origin tag. Pause, edit, delete, the steps and the cause it prevents are in the drawer.
  • "Not yet covered" rows list machines without a maintenance programme and probes without a calibration; each opens a prefilled schedule. The library's rule gives every probe a monthly calibration: for a probe the library defines, that calibration has a library ID (<sensor lid>/CAL) and follows, updates and resets like any library item.
  • Add, edit, delete schedule. Drawer: 1 what work, on what (plant, unit process, control group, machine; routine | preventive | calibration with its probe); 2 how often (calendar | run-hours | whichever first, every n unit, n run-hours from the machine's run status (or a counter), counted from fixed dates or the last completion, next due, grace days); 3 who and how (our team or a vendor, statutory, Lead sign-off, hours, parts); 4 steps and the cause it prevents (library references).
  • Changing the name, flow or cadence of an inherited schedule is a local change, as on alerts; the drawer shows both IDs and Reset to library.
  • Run-hours come from the machine's run status: the engine counts the time spent in its category's run state (Running) with COUNTIF. The drawer offers the machine's run status first, then any counter; a machine with neither has calendar cadence only, and the drawer says why.
  • A Lead may change only the cadence of in-house preventive maintenance; everything else is read-only for a Lead.

5.7 The library check, inside Step 2 a collapsible panel

  • The funnel, per plant, as a panel at the top of Sensors. Its summary line says how many sensors the library expects, how many are installed, recorded as not installed, missing, and how many offered items wait; it opens by itself when something is missing. Machines with every expected sensor installed and nothing offered are not listed.
  • One card per machine (and per stage and for the plant): a table of the sensor tags the library expects for its type (tag, unit, kind, and which alerts, run-hours schedules and calibrations need it) against the sensor tags installed as SCADA reports them: Installed | Missing | Not installed with reason, who, when. No value is read from the plant; it is configuration against configuration.
  • Missing → ＋ Add the sensor tag opens the reading drawer prefilled from the library's definition, on that machine. Missing → Not installed… asks for a reason and records it; the library items that need the sensor become Skipped instead of Blocked, and the export names the gap under knownGaps. Expect it again reverses it.
  • Under each card, what the library offers for that subject: Offered (with Inherit), Blocked (with what it needs), Skipped (with the recorded reason), Placeholder (with the pending decision).
  • A machine without a type or a stage without a profile is called out: the library cannot say what it should have.
  • People are not here. The console shows nothing about the roster, the ladder or quiet hours; they live in User Center.

5.8 Step 5 · Go live #/plant/:id/live

  • Checklist in tab order. Blocking (red): machines exist, every machine typed, every active alert valid, at least one active alert (a valid draft alert counts as on its way: Activate all drafts clears it), no drafts. Non-blocking (amber): the library check settled, no manual override in force, readings valid, limits complete, every machine with a reading watched, maintenance programme complete, nothing left to inherit.
  • Banner: Not live yet (n things) → Almost (activate drafts) → Ready (Go live) → Live (Back to draft). Activate all drafts activates only those that pass validation. Go live asks first, naming what will fire (active alerts, active schedules, missed-entry triggers) and how many drafts stay silent; Back to draft asks first and says that nothing fires while the plant is a draft. Both are audited. A plant with no active alert is never shown as Ready, on its card or its step.
  • Download the hand-off JSON (section 9). Under it, "Decisions still pending": the placeholders as a collapsed list.

5.9 History #/plant/:id/history · #/audit

  • Per plant and across the estate: when, who, plant, what, detail; searchable; newest first; 24 months. The list shows the newest 200 and says so, with Show all.

5.10 Library #/library/:section · a Global Admin edits, everyone else reads

  • Filter cards. Ten cards at the top, each a count and a filter: Plant types, Stage profiles, Equipment types, Signal categories, Alerts, Schedules, Data inputs, Formulas, Flows, Versions. The highlighted card is the list shown. Alerts are grouped by equipment type; schedules by plant type (plant-wide rounds), stage profile (stage rounds) and equipment type (planned work); data inputs by plant type, stage profile and equipment type; formulas by plant type and stage profile. Every row opens a drawer. A row for an alert, schedule, round, data input or formula opens the drawer of the type, profile or plant type that holds it, with that item expanded. For anyone but a Global Admin the drawer is read-only.
  • Library IDs. Every library item has an ID that never changes: T-centrifugal-blower for a type; under it /S- a sensor, /A- an alert, /W- planned work, /G- a group sensor (for example T-centrifugal-blower/S-line-pressure); P-bio for a stage profile with /R- rounds, /S- sensors, /I- data inputs, /F- formulas; PT-STP for a plant type with the same children; C-trip for a signal category; under a type, /I- a data input for every machine; a flow's own id. Items that existed before get IDs made once from their names; new items get a random suffix. Each item in a drawer shows its ID. An alert names its sensor by ID (sensorLid), so renaming the sensor keeps the alert on it.
  • Equipment type drawer: 1 the type (name, tag prefix, criticality, retired); 2 sensors it should have, each with unit, kind, range and preset bands on the coloured band bar (a state sensor names its signal category instead; a counter has none); 3 alerts, each watching one of the sensors on the machine or its stage, using that sensor's preset bands (on a state sensor: the states that raise it, the severity, and the minutes in that state), with its fix flow; 4 planned work (routine or preventive, every n units or n run-hours, steps, hours, parts); 5 data inputs for every machine of the type (a value with preset bands, or a state with the states that raise its alert); 6 sensors the group should have when two or more run together. Items are collapsible rows with Remove; ＋ adds one and opens it.
  • Signal categories: each row shows the states with the problem ones marked, the SCADA codes, “counts run-hours” for a run status, and how many library sensors and plant readings use it. The drawer: name, SCADA codes, note; the states, each a whole-number value, a name and A problem | Normal | Information, with ＋ State and Remove (at least two); Counts run-hours: No, or the state that means running. Nine come with the library: Run status, Trip, Fault, Flood switch, Auto / manual, Hooter, Valve open, Valve closed, Yes / no check.
  • Stage profile drawer: name and keywords (a SCADA zone whose name contains one gets the profile), rounds, sensors the stage should have, data inputs with preset bands, formulas with each name bound by reading name. Plant type drawer: plant-wide rounds, data inputs and formulas. Flow drawer: name, used for (fix, preventive maintenance, round, calibration), machine types, steps one per line.
  • Draft and publish. The first save starts a draft; the banner counts the changes and offers Review and publish, or Discard draft. Items changed in the draft carry a chip. Saving without a difference records nothing. Publishing shows the changes, takes notes for the plants, and stores the whole library as a new version named by date (v2026.10.19, then v2026.10.19.2 the same day). Alerts take their bands from the sensor's preset at publish.
  • Rules: names are required and unique within their list; bands deeper means worse and inside the range; an alert must watch a sensor that has preset bands, and a sensor has at most one alert; every name can change, because plants follow items by library ID: a renamed sensor keeps its alerts, its plant readings and its Not installed records; a renamed alert, planned work, round, data input or formula reaches plants as a name change on their next update; renaming a type renames its machines at every plant when the version is published, and the SCADA type map, flows, stage profiles and inherited items follow; a type that machines use cannot be deleted, only retired; a retired type is not offered for new machines and machines that have it show it as needing attention; a profile or flow in use cannot be deleted; a state sensor needs a category, and its alert a severity and at least one state but not all; two alerts on one state sensor are fine when their states differ; a category needs a unique name, at least two states with unique whole-number values and unique names, a run state (if set) that is one of them, and SCADA codes no other category has; a category that any library sensor, group or stage sensor, data input or plant reading uses cannot be deleted. Publishing is refused while the draft removes a type, profile, flow or signal category that plants use, removes a state that a library or plant alert is raised in, or stops a run status counting run-hours that plant schedules count from. The change list is a comparison of the draft with the published library, so an edit undone by hand leaves no change, and a draft with no difference is dropped. Every publish and discard is in the History.
  • Versions: every published version with date, author, changes and notes, and every plant with the version it follows.
  • At a plant: when a newer version is published, the plant header and its card say so. Opening it shows exactly what updating changes, only for items that still follow the library, matched by library ID: names (an alert keeps its subject, for example " — BL-1"; a field the plant changed locally is skipped), bands on readings (the library alert on the reading re-derives its closing value; removed bands switch that alert off), flows on alerts, cadence and run-hours (removed run-hours mean calendar only) and steps on planned work, the steps of flows the plant runs (a plant keeps the steps it had until it updates), criticality on machines without an override. Data inputs added to an equipment type appear as offers on every machine of that type. A state alert that still follows the library takes the library's new states, severity and hold (State alerts), and a reading takes its library sensor's or data input's new category (Signal categories); a plant that changed an alert's states, severity or hold keeps them as a local change. Alerts on data inputs and formulas follow their name too, and readings whose library sensor was removed keep their bands as the plant's own. Changes to a data input's cadence, who enters it or its missed severity, and to a formula's expression, reach a plant through Reset to library on that reading. It also lists items no longer in the library (they become custom and stay), machines on a retired type, the number of items that keep their local changes, the number of custom items that stay as they are, and new offers waiting in the library check. A Site or Technical Admin applies it; it is audited.

5.11 State signals and run-hours acceptance criteria

Many sensors in the fleet report a state rather than a measurement: on/off, trip, auto/manual, flooding, hooter, valve open, valve closed, and more. SCADA creates each such sensor with its signal category; the library defines the categories as part of the perfect set; the engine counts time in a state with COUNTIF (decisions S1–S4). Each criterion below is testable in the prototype; SS-14 is the upgrade the build runs on saved configurations.

  • SS-1 · Categories live in the library. The Library has a Signal categories card. A Global Admin can add, edit and delete a category (name, SCADA codes, note, at least two states each with a value, a name and a role, and an optional run state); it saves to the draft and reaches plants when published. Everyone else reads it.
  • SS-2 · A category in use is protected. A category that any library sensor, data input or plant reading uses has no Delete; publishing a draft that removes one is refused with the category's name. Publishing is also refused when the draft removes a state that an alert is raised in, or takes away the run state that run-hours schedules count from.
  • SS-3 · SCADA creates the sensor with its category. A state reading that SCADA brings shows its category read-only, with the states and what each means. Kind is read-only too. A tag code the library knows (TRIP, RUN, FLOOD, FLT, AM, HOOT, VO, VC) resolves to its category when SCADA sends none.
  • SS-4 · States are shown by name. In the Sensors list a state reading reads “state · Trip”, its sample “Healthy”, and “Tripped is a problem”; an information-only category reads “information only”. States show by name and ON/OFF never appears; a sensor never says what it raises, only an alert does.
  • SS-5 · A state is never banded. A state reading has no unit, valid range input or severity bands; its range comes from the category's values. Switching a reading to State clears its unit and bands.
  • SS-6 · An alert picks the states that raise it. Picking a state reading on an alert ticks the category's problem states (none for an information-only category such as Run status), sets Major (an inherited alert takes the library's severity), hold 0, and closes when it leaves that state. The user can tick other states, change the severity, and set “in that state for at least n minutes”. With no state ticked, every state ticked, or more than one severity, the alert says why, is kept as a draft and cannot be activated. Several alerts may watch one state sensor when their states differ (Travelling raises a Minor, Jammed a Major); two alerts raised in the same state get a warning.
  • SS-7 · Time in a state is counted by the engine. With no hold the export's engine formula is [TAG] = v, or OR([TAG] = 1, [TAG] = 2) for several states. With a hold it is AND(COUNT([TAG], "10m") > 0, COUNTIF([TAG], "=v", "10m") >= COUNT([TAG], "10m")): every sample in the window was in that state, and there was at least one sample, so an offline sensor raises nothing. Several states add their COUNTIFs (COUNTIF(…"=1"…) + COUNTIF(…"=2"…)); a 60-minute hold is written "1h". The band's condition is in the chosen values and severityBands[].states carries their names; the close condition is notIn the same values.
  • SS-8 · Manual is only reported. The Auto / manual category is information only: no alert is offered on it by default, and Manual never quiets or suppresses another alert. Suppression stays with Under maintenance (F14).
  • SS-9 · Run-hours come from run status. The seven types that had an hour counter (centrifugal blower, hypochlorite dosing unit, progressive cavity pump, submersible pump, screw press, filter press, air compressor) now have a Run status sensor (category Run status, run state Running) instead; the drawings' hour tags became run switches. The schedule drawer lists the machine's run status first. A run-hours schedule names that reading; the export carries meterSource: "runStatus" and, on the reading, runHours.engine: COUNTIF([RUN-…], "=1") * SAMPLE_HOURS. A counter (throughput) can still drive a schedule as meterSource: "counter", never an alert.
  • SS-10 · Data inputs where they live. Every group header in Sensors, and the unit process, control group and machine drawers, offer ＋ SCADA tag, ＋ Data input and ＋ Formula, opening the reading drawer on that subject with that source chosen. A data input made on a machine gets a tag ending with the machine's tag (MAN-…-BL-1).
  • SS-11 · A person can record a state. A data input's kind can be State or yes/no with a category (for example Yes / no check). Its sample is a state; an alert on it picks states like any state alert; when the input has a missed severity, a missed entry raises its own issue.
  • SS-12 · Equipment types carry data inputs. The type drawer has Data inputs for every machine. Each is a value (with preset bands) or a state (with the states that raise its alert and the severity). After publishing, every machine of the type is offered each input in its library check; applying one makes the reading on the machine and, when set, its alert, both linked by library ID and covered by Reset to library and the update plan.
  • SS-13 · Library sensors and alerts on states. In the type drawer a State sensor asks for its category instead of a unit and bands; an alert on it shows the category's states as tick boxes, the severity and the minutes in that state. Validation refuses a state sensor without a category, and an alert on one with no severity, no state, every state, or a state the category lacks.
  • SS-14 · Saved configurations upgrade. On every load, a state reading without a category gets it from its library sensor, its library data input or its tag code; its range becomes its category's values and any limits on it are cleared; a state alert becomes a single-severity alert on state 1 (what “fires on ON” meant); loading twice changes nothing more. The prototype itself starts fresh under a new browser key, because its hour counters became run statuses; the build runs this upgrade on saved plant configurations.
  • SS-15 · Information-only states need no alert. A machine whose only sensors are information-only states, such as its run status, is not listed as Nothing watched; a sensor with a problem state is.

7 · Data inputs and formulas

7.1 Data inputs: a value a person enters

A reading with input: "manual". The console sets what the library or the person decides: the cadence (every n shifts, days, weeks or months), who enters it (Operator or Lead), what happens when nobody does (nothing, a Caution, or a Minor issue). The operator app owns the entry screen Manual entry screen; it writes the value as a reading, after which alerts on it behave like any other.

  • A missed entry is an issue of its own: the console exports a missedEntry trigger per manual reading with a missed severity (section 9). It fires at the end of the cadence window; no grace period (decision F7).
  • A lab value is one sample: alerts on manual readings default to hold 0 and close when the next value is back in band.
  • The library offers data inputs by plant type (STP: inlet COD, outlet COD, outlet BOD, outlet TSS; ETP: inlet COD, outlet COD, outlet TDS, outlet oil and grease; WTP: raw water turbidity, residual chlorine) and by unit process profile (MLSS and SV30 for a biological stage; head loss for filtration). Each comes with its limits and its alert.
  • The library offers data inputs by equipment type too: every machine of the type is offered them, tagged with the machine (MAN-BEARING-VIBRAT-BL-1). In this build: Bearing vibration (handheld, weekly, mm/s, Minor above 4.5, Major above 7.1) on centrifugal blowers, and Pump sump dry and clean (a daily yes/no; No raises a Minor issue) on submersible pumps.
  • A data input can record a state instead of a value: a yes/no check or any signal category. Its alert raises in the states the library or the plant ticks; a missed entry is still its own issue.

7.2 Formulas and the analytical engine

The analytical engine is both the trigger engine and the computation engine (decision F5). Every enabled sensor-level alert becomes an engine formula in the backend; every computed reading is an engine formula; a missed data input is an engine formula on the age of a tag. The console is where people write and edit these in plain terms. The compile step turns each into engine: {dialect: "hyperformula", formula, upsertKey}, and an edit re-sends the same key so the engine replaces rather than duplicates.

7.3 The funnel: the perfect picture against the actual plant

The library holds the perfect picture of each machine type, stage and plant type: the sensors that should be installed, and every alert, schedule, round, data input and formula that follows from them. A real plant is never the perfect picture: a flow meter was not in the contract, a trip contact was never wired, a stage was built without a probe, a sensor is on order. SCADA reports what is actually installed. The console puts the perfect picture and the actual plant side by side and makes every difference explicit, so that nothing the library expects is silently lost and nothing irrelevant keeps nagging.

  • Compare. Configuration against configuration; no value is read from the plant. For each machine with a library type: the sensor tags the type expects, against the sensor tags installed on that machine as SCADA reports them. For each stage and each group: the sensor tags the library expects by profile and by the members' type (decision F15), against the tags installed on them. For each stage and for the plant: the rounds, data inputs and formulas offered, against what has been taken. For each miss, which library alerts, run-hours schedules and calibrations depend on it.
  • Settle each miss one of two ways. Add the sensor tag (the sensor exists, SCADA just did not bring it), prefilled from the library's definition. Or record it as not installed, with a reason, by whom, since when.
  • Consequences of a record. Suggestions that need the sensor move from Blocked to Skipped with the reason shown; they stop counting as pending; the export lists the record under knownGaps; a new library version that still expects the sensor does not re-flag it. Expect it again reverses all of this.
  • What is not compared yet. Connections (readings on pipes and neighbours) and condition-based work are placeholders. The funnel is written so those join as more rows, not as a new screen.
